# 实现原理

这份文档解释"为什么这么做"，以及几个必须绕开的 macOS 权限坑。想改代码前建议先读一遍。

---

## 一、云枢的进程结构（方案的事实基础）

在 macOS 27 / 云枢 2.6.1.33 上实测：

| 组件 | launchd 标签 | 域 | 程序 | 特性 |
|---|---|---|---|---|
| 主程序（菜单栏 UI） | 无（登录项 `2.com.eagleyun.sase`） | 用户 | `/Applications/Yunshu.app` | 点「连接网络」才建隧道 |
| 用户级代理 | `com.eagleyun.endpoint.agent` | `gui/501` | `/opt/.yunshu/YunshuAgent.app` | `KeepAlive` |
| 服务管理器（建隧道） | `com.eagleyun.sase.servicemanager` | `system` | `/opt/.yunshu/YunshuManager.app` | `KeepAlive`，拉起 FWRunner / TBRunner / TBEngine / dpengine |
| 特权助手 | `com.eagleyun.sase.helper` | `system` | `/Library/PrivilegedHelperTools/com.eagleyun.sase.helper` | `KeepAlive` |

**隧道识别**：点对点 `utunN` 上有一条 inet 地址（实测 `10.251.1.1`），且**大量路由的网关等于该地址**（实测 361 条）。脚本按这个特征判断，不写死接口名和网段，云枢换网段也不受影响。

```zsh
netstat -rn -f inet | awk '
  $NF ~ /^utun/ { c[$NF " " $2]++ }
  END { for (k in c) if (c[k] > n) { n = c[k]; best = k }
        if (n >= 5) print best, n }'
```

一次 `netstat` 聚合所有 utun（早期版本按接口逐个查，7 个接口 ≈ 1.6 秒，现在 ≈ 0.07 秒）。

### 一个被实测证伪的假设：`CONNECT` 偏好键

早期版本曾假设 `defaults write com.eagleyun.sase CONNECT -bool true` 等于客户端「设置 → 自动连接内网」，
可以做到"启动即连、零点击"。

**实测证伪**：把 `CONNECT` 写成 1、退出再启动云枢，20 秒内隧道没有建立，而且程序启动后又把 `CONNECT` 改回了 `0`。
日志里只有 `user auth success` / `is_authed = 1`，没有任何发起连接的记录。

结论：`CONNECT` 只是**状态回写位**，不是可写的开关。**连接动作只能由界面发起**，
因此「辅助功能」权限是必需项，不是可选项。

## 二、为什么直接操作 launchd，而不是禁用进程

柠檬之类工具的「禁用进程」是在进程层做拦截，遇到 `KeepAlive` 的 launchd 任务会被反复拉起，状态也不透明。

直接操作 launchd 才是这套程序的原生开关：

- `launchctl disable system/<label>` → 写入持久化禁用表，**重启后仍有效**，`KeepAlive` 失效；
- `launchctl enable` + `bootstrap` + `kickstart` → 精确还原，不用重装；
- 状态可读：`launchctl print` / `launchctl print-disabled`。

所以本方案不需要任何第三方软件，也不留常驻 root 进程。

## 三、提权模型：受限 root 助手 + sudoers

`up` / `down` 要操作 `system` 域的任务，必须 root。可选的两条路：

| 方式 | 问题 |
|---|---|
| `osascript ... with administrator privileges` | **每次都要现场授权，从不缓存**，就是那个「允许管理员访问由 zsh 启动的脚本吗？」 |
| 常驻 root 守护进程 | 权限过大，用户不可控，卸载也麻烦 |

本项目的做法：

1. `lib/yunshu-priv` 装到 `/usr/local/sbin/yunshu-priv`（`root:wheel 0755`，普通用户不可写）；
2. `/etc/sudoers.d/yunshu-switch` 只放行三条**精确匹配**的命令：

   ```
   shiwuhao ALL=(root) NOPASSWD: /usr/local/sbin/yunshu-priv check
   shiwuhao ALL=(root) NOPASSWD: /usr/local/sbin/yunshu-priv up
   shiwuhao ALL=(root) NOPASSWD: /usr/local/sbin/yunshu-priv down
   ```

3. `ysctl` 用 `sudo -n` 调用它，**不弹密码框**；没装助手时自动退回密码框方式（功能不减）。

助手脚本自身的安全约束：

- 只接受 `check` / `up` / `down` 三个子命令，其余直接拒绝；
- `$EUID -ne 0` 立即退出；
- `launchctl` / `pkill` 全部写绝对路径（`/bin/launchctl`、`/usr/bin/pkill`），不读 `PATH`；
- 不接收、不拼接任何外部参数。

> **踩过的坑**：`check` 在规则里、`up`/`down` 漏了，会出现"探活通过、`doctor` 显示 ✅、真跑起来却要密码"的诡异现象。
> 1.2.0 起 `ysctl fix` 会把三条规则整体重写；`priv_run` 也会区分"sudo 自身没跑起来"与"助手执行了但返回非 0"。

## 四、界面自动化为什么放进 App 里

「连接内网」最后一步是在云枢界面点「连接网络」。两条路都试过：

| 方案 | 结果 |
|---|---|
| `osascript` + System Events | 报 `-25211 osascript 不允许辅助访问`；授权对象是终端/osascript，换终端就失效 |
| Apple Events 发 `quit` | 报 `-10004 发生权限违例`（缺「自动化」授权） |

最终方案：**App 自己用 `AXUIElement` 遍历云枢窗口与状态栏附加菜单**，按标题 / 描述 / 值 / 帮助文本匹配按钮后 `AXPress`。
用户只需给 App 授权一次「辅助功能」，与终端无关；退出程序改用 `SIGTERM`（避开 Apple Events）。

实测细节：

- 云枢的按钮文案是「**连接网络**」/「**断开网络**」（不是"立即连接"），且按钮在**状态栏的附加面板**里，
  需要先 `AXPress` 状态栏图标把面板打开；
- 冷启动的头几秒，云枢的可访问性树是**空的**（日志 `elements=0`），此时找按钮必然失败；
- 点下去可能返回成功但**云枢静默不理会**（本地服务还没接上），隧道永远不建立。

对应措施：

1. **0.1 秒轮询**，树一出现立刻点（原来是"查一次睡 1 秒"，前三轮白睡 3 秒）；
2. 点完盯**菜单文案**（`连接网络` ⇄ `断开网络`）4.5 秒，没翻转说明点空了 → 自动补点；
3. `ysctl` 侧最多 3 轮兜底，仍失败则**重启云枢主程序再点一次**；
4. **顺序不能乱**：必须先起系统守护进程 + 用户级代理，再启动主程序。反过来实测稳定触发"静默空操作"。

## 五、CLI 与 App 的通信协议

App 是唯一持有「辅助功能」授权的进程，所以 CLI 需要借它点击。两者通过两个文件通信，无需端口、socket 或额外授权：

```
~/Library/Application Support/YunshuSwitch/
├── ax.request    两行：随机 nonce + 命令（connect / disconnect / dump / trust）
├── ax.response   两行：同一个 nonce + 结果（OK / NOAX / NOUI / NOBTN / TIMEOUT）
└── ax.status     辅助功能授权状态 trusted/untrusted + App 的 pid
```

- App 每 0.1 秒轮询 `ax.request`，读到就**先删再执行**（防重复），结果写回 `ax.response`；
- CLI 写入后按 0.1 秒轮询响应，最长 30 秒，用 nonce 校验避免读到上一次的残留；
- `ysctl status` 直接读 `ax.status` 判断授权，**不会为了查状态而拉起 App**；
- App 没在跑时，`ysctl` 按 bundle id（`com.shiwuhao.yunshuswitch`）重新拉起并等最多 12 秒。

## 六、性能：时间都花在哪

先分清两部分：**脚本自身开销**（能优化的）和**云枢自己干活的时间**（优化不掉的，建隧道 2~5 秒、拆隧道 0.5~1 秒）。

| 场景 | 1.0 | 1.1 → 1.3 |
|---|---|---|
| `up` 脚本开销（不含云枢建隧道） | ≈5.1 s | **≈1.2 s** |
| `up` 总时长（主程序冷启动） | 7.9 s | **5.4~6.5 s**（差额全在云枢建隧道） |
| `down` 脚本开销 | ≈2.0 s | **≈0.9 s** |
| `state` | 0.45–0.55 s | **0.18–0.30 s** |
| `status` | 0.72–0.83 s | **0.5–0.7 s** |

更早（1.0 之前）：`up` 约 25 秒且冷启动常失败（`NOBTN`）、`down` 12.7 秒还残留 4 个 root 进程、`state` 0.85 秒、`status` 1.84 秒。

| 环节 | 旧做法 | 现在 | 手段 |
|---|---|---|---|
| 等云枢界面就绪 | 每轮"查一次 → 睡 1 秒" | 0.1 秒轮询 | 事件驱动 |
| 判断点击是否生效 | 无，失败只能干等 45 秒 | 看菜单文案，4.5 秒没翻就补点 | 自我修复 |
| 等隧道建立/拆除 | 0.3 秒一轮，且轮数算错（45 秒只等 27 秒） | 墙钟 deadline 0.15 秒一轮 | 修 bug + 加速 |
| 隧道识别 | 每个 utun 跑一次 `netstat` | 一次 `netstat` + awk，加 0.6 秒缓存 | 聚合 + 缓存 |
| 系统守护进程 | `kickstart -k` 强制重启 + `sleep 1`（≈11 s） | ≈0.6 s | 只 `bootstrap`，没起来才 `kickstart` |
| 用户级代理 | `kickstart -k` + `sleep 1`（≈11 s） | ≈0.3 s | 先查状态，未运行才拉起 |
| 等主程序 / 代理就绪 | 固定 `sleep 0.4`×3 | poll 0.05 秒 | 事件驱动 |
| 残留校验 | 固定 `sleep 1` | 先查，不干净才等（上限 1 秒） | 事件驱动 |
| 日志时间戳 | 每条 fork 一个 `date` | zsh 内建 `strftime` | 少几十次 fork |

> ⚠️ 守护进程那两项的提速落在**系统里的** `/usr/local/sbin/yunshu-priv` 上。改完 `lib/yunshu-priv`
> 必须 `ysctl setup --force` 才会同步过去（一次性密码），`ysctl doctor` 会提示"版本落后"。
